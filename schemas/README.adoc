== The freeze rule

A **frozen** version is a promise about bytes, not about intent:

. its file is never edited and never re-issued — a change is a new version in a
  new file, listed beside the frozen one;
. its BLAKE3 digest is recorded in `index.json` *and* pinned in the crate, so an
  edit fails a test (`the_frozen_0_4_0_schema_is_still_the_file_this_build_was_tested_against`)
  rather than quietly changing what a pinned consumer reads;
. it stays readable. `pons validate-report` accepts every frozen version, and the
  version declared *inside* the document selects the schema it is validated
  against — so an old report cannot be validated against a new shape, and a new
  key cannot hide behind an old version number.

`index.json` is itself checked: every listed file must exist, must carry its
version in its name, and must match its recorded digest
(`the_schema_index_attests_every_published_contract_file`). Exactly one scan
envelope is marked `current`, and it is the version the binary emits.

== Adding a version

. Write the new file; never touch an existing version's file.
. Add it to `index.json` with `"status": "current"`, and mark the previous one
  `"frozen"`.
. If it is the scan envelope, bump `SCHEMA_VERSION` in
  `crates/pons-core/src/report/json.rs`, update `FROZEN_SCHEMA_VERSIONS`, add the
  frozen digest constant, and add an arm to `validator_for_version`.
. Update the shape test, Appendix G of `docs/PLAN.adoc`, and the version history
  there and in `CHANGELOG.adoc`.
. Re-bless the verdict matrix only if the policy itself changed
  (`PONS_BLESS=1 cargo test -p pons-core`), and say why in the changelog.

A version constant nothing checks is a comment, not a contract: every step above
that can be checked automatically is.
