= Scan envelope 0.5.0 (0.4.0 frozen) / exchange contract 1.0.0

`evidence_contract` carries the observed target Git commit (null outside Git),
execution outcome, native parser inventory and independently identifiable
records. Target `dirty` is always null (unknown): Pons avoids running target
Git status/diff operations that could execute configured filters or monitors.
Every analysed file includes a BLAKE3 digest of its original bytes.
Excluded/unsupported/unreadable contents are not hashed; these digests are not
represented as a digest of the entire repository. Dirty input can differ from
the named commit. Tool metadata contains its build-time source commit and dirty
state as well as package version. Git provenance is observational, not signed.

Each record includes producer, correlation group, rule, root-relative path,
line, tier, evidence class, qualitative confidence, trace, assumptions,
counterconditions and unknown edges. Pons-native T0 records share an AST
heuristic correlation group. Agreement with panic-attack or Sanctify must not be
counted as independent proof merely because producer names differ: shared
rules, models, parser sources and fixtures can correlate their evidence.

== Versions, and what "frozen" means

`schemas/index.json` is the machine-readable inventory: per artifact, its
version, file, whether that version is `frozen` or `current`, and the BLAKE3
digest of the bytes Pons was tested against. Three rules hold it together:

* A **frozen** version is never edited and never re-issued. `scan-0.4.0.json` is
  byte-pinned by `FROZEN_0_4_0_SCHEMA_BLAKE3` in
  `crates/pons-core/src/report/json.rs`, so an edit fails a test rather than
  changing what a pinned consumer reads.
* A change is a **new version in a new file**, listed beside the frozen ones.
* `pons validate-report` accepts every frozen version as well as the current one,
  and the version declared *inside the document* selects the schema it is
  validated against. A 0.4.0 declaration carrying a 0.5.0 key is rejected, and a
  report pinned at 0.4.0 still validates.

`0.5.0` is the envelope emitted by this build. Against `0.4.0` it adds three
keys, all appended and all additive — no key was renamed, moved or retyped:

[cols="1,2",options="header"]
|===
|Key |Why it exists

|`findings[].semantic_fingerprint`
|The cross-producer corroboration key. A verdict grid can mark one site once
instead of adding Pons's finding to panic-attack's or Hypatia's at the same line.

|`counts.actionable`
|`counts.total` minus the demoted count: the number an aggregating consumer
sums. Published rather than left to subtraction, so the demotion is a number in
the document rather than a convention a consumer might miss.

|`counts.demoted_speculative`
|How many findings are demoted as guesses. Equal to `by_evidence.SPECULATIVE`,
published twice on purpose: a consumer reading only the aggregate must see it.
`validate-report` rejects a document whose `actionable + demoted_speculative`
does not account for `counts.total`, or whose demoted count disagrees with
`by_evidence`.
|===

== Corroborating a Pons finding against another producer

Each finding carries `semantic_fingerprint`: 64 lowercase hexadecimal characters,
BLAKE3 over

....
pons-corroboration-v1 NUL root-relative-path NUL 1-based-start-line NUL evidence-class
....

with NUL (`0x00`) as the field separator and the evidence class spelled exactly
as the envelope spells it (`HEURISTIC`, `DATAFLOW`, `PROTOCOL`, `SPECULATIVE`).
The path is the same root-relative, `/`-separated spelling records use, so a key
survives a checkout move. A consumer can mint the same key for a foreign
producer's finding without running Pons; `schemas/verdict-matrix-1.0.0.json`
publishes the recipe and the token that identifies it.

What the key is for, and what it is not:

* Same key means **same path, same line, same evidence class** — a site, not a
  defect. Two Pons rules firing on one line in one class share a key by design,
  and so do two producers. The grid counts that site once and keeps both
  findings' provenance.
* It deliberately **ignores the rule id, the producer and the severity**, so it
  stays stable when a rule's severity is tuned. Severity is advisory; the
  evidence class is the honesty invariant.
* It is **not** the record fingerprint. `evidence_contract.records[].fingerprint`
  identifies one finding (rule id plus a whitespace-folded anchor) and survives
  blank-line insertion; this key identifies one site and survives a rule rename.
  Both are identifiers, neither is a semantic-equivalence proof.
* Every finding's `location.file` must be expressible **inside** the scan root.
  A path that cannot be made relative — an absolute file elsewhere on the
  machine, or one climbing out with `..` — is rejected rather than substituted
  unchanged, because a key minted from it would encode the build machine and
  match nothing a consumer can derive.
* The `counts.*` figures count **findings**, while corroboration collapses
  **sites across producers**. Two Pons rules firing on one line in one class are
  two findings sharing one key; a Pons finding and another producer's finding at
  the same site are one corroborated site. Both directions are published in
  `schemas/verdict-matrix-1.0.0.json` (`aggregation.rules`).
* A `SPECULATIVE` key **corroborates nothing**. Agreement between two guesses is
  two guesses; the demoted bucket is excluded from every verdict.
* Agreement is corroboration, not independent proof. Shared rules, models,
  parser sources and fixtures correlate evidence across producers, and
  `validate-report` cannot detect that — only the consumer, holding both
  provenance records, can.

== Severity × evidence, published as data

`schemas/verdict-matrix-1.0.0.json` states, for all twelve
(severity, evidence class) pairs, what an aggregating consumer must do with a
finding:

* `aggregate_weight` — `severity weight (INFO 1, WARN 2, ERROR 3) × evidence
  weight (HEURISTIC 50, DATAFLOW 80, PROTOCOL 70, SPECULATIVE 0)`. **Zero for
  every speculative cell**, whatever severity the finding claims: a guess adds
  nothing to a sum.
* `sarif_level`, `counts_toward_verdict`, `gate_eligible`, `count_bucket`
  (`actionable` or `demoted`) and `demotion_suffix`.

`sarif_rank` (50/80/70/20) is also published and is a *different number* from
the weight: it is how much attention Appendix E's `rank` asks a viewer to pay,
and speculative findings keep their 20 so they stay visible. Visible, not
counted — collapsing the two would either hide guesses or inflate totals.

The document is generated from `crates/pons-core/src/verdict.rs`, which is also
where the SARIF reporter, the SARIF rank table, the confidence labels and
`--fail-on` get their values; `the_published_matrix_matches_the_code` fails if
the committed file and the code disagree.


Fingerprints use BLAKE3 over rule ID, root-relative path and a whitespace-folded
source anchor plus occurrence ordinal. Checkout relocation and added blank
lines preserve them. Renames, changed anchors and insertion of an identical
occurrence can change them. They are identifiers, not semantic-equivalence
proofs. Exact duplicate rule/location findings are deduplicated; broad categories
are never silently suppressed.

`pons validate-report FILE` rejects unknown schema versions, missing inventory,
contradictory coverage/counts, malformed fingerprints, inconsistent tier/evidence
and mismatched record/finding rules. Success validates the schema, not the
security of the target. Consumers must also inspect scan exit status and
coverage. `scanned.inventory[].analysis_complete` is relative to the registered
models; it never certifies full language semantics.

Suppression migration: non-empty `suppress.rules` and `suppress.paths` lists are
now errors. `suppress.allow` requires rule, path, reason, owner and future
`expires` in Unix seconds. Inline directives require the same metadata, with
the adjacent line as their scope. Malformed/expired inline allowances do not
hide findings. Coverage accounting never consults suppression.

== Consumer integration examples

[source,sh]
----
# Preserve the scanner status even when collecting output on an incomplete run.
# Use an absolute temporary directory OUTSIDE the target checkout. Shell
# redirection creates the report before discovery; never scan your own output.
report_dir=$(mktemp -d /tmp/pons-evidence.XXXXXX) || exit 2
rc=0
pons scan . --format json --fail-on-skips --require-language php > "$report_dir/pons.json" || rc=$?
pons validate-report "$report_dir/pons.json" || exit 2
# Upload "$report_dir/pons.json" even when rc is nonzero; do not relabel it clean.
exit "$rc"
----

For panic-attack, retain its native report alongside `pons.json`. An adapter can
consume contract 1.0.0, keeping producer and correlation group unchanged.
No panic-attack producer/consumer implementation is claimed by this repository.
Sanctify CI must report Haskell as unsupported by Pons and preserve Sanctify's
own compiler/parser execution outcome; an empty result after parse failure is
not acceptable evidence. Wharf CI may emit instrumented event arrays and run
`pons wharf-trace`; it must retain the events and substantiate verification and
durability assertions. No source-to-event extraction is provided yet.

== Implemented rule/evidence matrix

[cols="3,1,2,4",options="header"]
|===
|Rule |Tier |Adapter |Scope / main limit
|div-by-literal-zero, self-assignment, constant-condition |T0 |Python, JS, TS/TSX, Rust |AST candidate; no runtime proof
|while-true-no-break, empty-effect-loop |T0 |Python, JS, TS/TSX, Rust |Local syntax; await is not proof of progress
|unreachable-after-jump |T0 |Python, JS, TS/TSX, Rust, PHP |Same-block adjacency; branch siblings and PHP labels are excluded
|swallowed-error, string-concat-in-loop |T0 |Python, JS, TS/TSX |Local syntax only
|dead-store, read-before-init |T1 |Python |Existing CFG may-analysis; opaque functions and infeasible paths disclosed
|php-empty-security-function |T0 |PHP |Name heuristic plus empty AST body
|php-unresolved-include |T0 |PHP |Literal source-relative filesystem observation
|php-context-flow |T1 |PHP |Bounded local CFG; context-specific may-flow, opaque unknown scopes
|explicit protocol and Wharf traces |T2 |Supplied events |Premise-dependent model conformance; no source extraction
|Speculative rules |T3 |None registered |Tier plumbing retained; no claim of implemented rules
|===

No rule applies to Haskell or Elixir source. Composer/WordPress interprocedural
resolution, PHP exception/finally flow, source-derived protocol extraction,
full PHP/runtime verification and independently validated production consumer
adapters remain work items. The labelled regression corpus measures fixture
behavior; it is not a representative real-world precision/recall estimate.

`execution.status=completed` records that a report-producing invocation finished;
`execution.exit_code` records the actual CLI outcome separately from coverage.
Library-only rendering uses null until a caller chooses a gate policy. This
prevents a findings-threshold exit or failed coverage gate being confused with a
successful assurance result. Protocol input is capped at 1 MiB; trace JSON
input is capped at 16 MiB, in addition to event-count/model bounds.
`validate-report` reads through a buffered reader with no fixed byte ceiling,
but still materializes the JSON value in memory. Use external CPU/RSS limits
for untrusted reports; buffered input is not bounded-memory validation.
