=== What is genuinely strong, and should not be disturbed

The evidence-class invariant (tier derives the class; `Finding`'s private
fields make a forged class unrepresentable), the frozen-schema discipline with
a recomputed digest, the falsifier gate with mandatory negative corpora, and
the `verdict.rs` single-gate refactor that makes the CLI, the human reporter,
SARIF and `Counts::tally` read one table. The 0.5.0 contract is the most
consumer-facing thing this repository has produced. Nothing below proposes
reopening any of it.

== Cross-repository clash analysis

This section exists because the most likely way to damage the estate from here
is to make other repositories fit *this* repository's shape.

=== The verdict-grid identity clash (metadatastician/standards)

`metadatastician/standards` already renders a `pons asinorum` row
(`scripts/lib/verdict-grid.jq`, `docs/VERDICT-GRID-SPEC.adoc`, VG v1.0 schema
3). Measured on that repository's `main`:

* Its cross-reporter fingerprint is `[normalised path, positive line,
  normalised class or CWE]`, where a pons finding's class falls back to its
  `rule_id`.
* Pons's new `semantic_fingerprint` is `BLAKE3(root-relative path, line,
  evidence class)`.

**These are different keys and must stay different.** The grid's third
component is a *defect* class; pons's is an *evidence* class. Substituting
pons's key into the grid would make every pons finding on a line collapse with
every other producer's finding on that line regardless of defect — a
`syntactic-heuristic` at line 40 corroborating an `sql-injection` at line 40.
That is precisely the over-merge the grid's `uncorrelatable_total` guard and
its "absent identity must never collapse distinct defects" comment exist to
prevent. Pons's own documentation claims that agreement "at the same line" is
one corroborated site; that claim is about a *site*, and the grid's stricter
model is the one that should win, because it is the only one that can tell a
heuristic overlap from a defect overlap. The honest resolution is a separate,
non-grading "site overlap" figure — never a replacement key.

=== Demotion is a number now, and it must land before T3 does

No T3 rule is registered, so `counts.demoted_speculative` is 0 and a consumer
that ignores it behaves identically today. That is the whole point of adopting
it now: the standards lane counts pons findings by `severity` alone, so the
first registered T3 rule at `INFO` renders "blue, minor" and at `ERROR` would
render purple. The contract says a speculative finding never counts toward a
verdict. Adopt the demotion while it is a no-op, not after the first guess
appears in a graded row.

=== Exit 2 means "no applicable input", and the consumer does not know that

Pons exits 2 when nothing applicable was analysed, and still prints a parseable
JSON envelope with `scanned.coverage_status == "no-applicable-input"`
(`docs/COVERAGE-MIGRATION.adoc`, ADR-0005 amendment). The standards lane
currently writes `status: error` for *any* non-zero exit, so a documentation-only
repository gets a permanent orange pons row reading "pons scan exited 2" —
missing evidence where the truth is "nothing to analyse". `cicd-suite`'s
`custom-tools-check` already maps that exit code to `not_run`, so the estate is
internally inconsistent about it, and the fix belongs in the consumer.

=== The release-dependency direction runs against the grain

`metadatastician/standards` builds pons from source by pinned SHA with a
ten-minute timeout and a `~/.pons` cache keyed by that SHA. That is a defensible
supply-chain posture, not a workaround. If pons cuts attested release binaries,
the lane *may* prefer them — but pons must not plan its release to suit one
consumer, and the lane must not relax its pinning to suit pons. The prompt below
asks the question and accepts "no" as an answer.

=== Tag signing is a hard wall for this environment

`Immutable-Tags` requires signed tags and declares **no bypass actors**. Every
agent session in this sandbox produces unsigned commits (measured above). So a
release tag cannot be created from here by any route; it needs a signing key on
the account or a human's signed tag. Any prompt that says "cut v0.1.0" is
therefore unsatisfiable as written, and the release prompt below says so
explicitly rather than letting a session discover it at the last step.

=== The vendored benchmark scripts gate P2

`scripts/proven-bench/` is vendored byte-for-byte from
`hyperpolymath/proven-tests-and-benches` with a digest check, so it cannot be
patched here. Two defects are already drafted for upstream
(`docs/handoffs/upstream-prompts.adoc` §8): `compute-bench-baseline.sh` accepts
an empty file as a validated run and then writes `window: 9` while its own
`MIN_RUNS=10` check is satisfied by *argument count*, and
`check-bench-regression.sh` silently compares against `$b[0]` of a multi-document
baseline. Pons has no baseline yet, so nothing is broken today — but P2's
performance gate writes the *first* baseline, which makes the upstream fix a
precondition rather than a nice-to-have.

3. CONSIDER PARTIAL ENROLMENT, WITHOUT WEAKENING THE DEFAULT.
The gate requires BOTH tools, so a repository that wants pons analysis on its

to both, where an explicitly requested tool must be on PATH or the gate exits 2,
would keep the current strictness by default. Optional — only if it does not
complicate the exit-code contract.

THE EXIT-CODE CONTRACT, since it is the thing most likely to be broken by a
future pons change. Pons ADR-0005 plus docs/COVERAGE-MIGRATION.adoc define:
  0 — analysis ran, findings (if any) below the --fail-on threshold; no
      --fail-on is passed by this gate, so 0 is the normal case;
  1 — findings at or above --fail-on. This gate does not pass --fail-on, so a
      1 here would mean pons changed its default; treat it as `failed`;
  2 — NO APPLICABLE INPUT: zero files analysed, or an operational error (an
      unopenable root, a bad config). Pons still prints a parseable JSON
      envelope for the coverage case, with scanned.coverage_status ==
      "no-applicable-input". not_run is the right mapping for both, but the
      reason string should quote which one it was, because "exited 2" alone
      cannot be diagnosed from a log.
If pons ever changes these semantics it will bump nothing — the exit contract
is an ADR, not a schema — so reference ADR-0005 in a comment and in the
README rather than restating the numbers as fact.

reason to reverse it.

=== S3 — hyperpolymath/proven-tests-and-benches: two defects that poison the first baseline

[source,text]
----
TASK: fix two validation defects in the benchmark scripts, and publish the

1. compute-bench-baseline.sh counts FILE ARGUMENTS, not validated run documents.

   file, so an empty file passes; the later `jq -s` then collects nine documents

   script's own MIN_RUNS=10 check was satisfied by the number of arguments. The
   gate is then mathematically inert, which is precisely what the script's

   file names.

2. check-bench-regression.sh accepts a baseline containing more than one JSON
   document: it uses `--slurpfile b "$BASELINE"` and reads $b[0], so a

   about the extra. Please reject a baseline that is not exactly one valid
   document, before comparing.

baseline today, so nothing is broken in that repository — its ledger entry is a

=== S4 — hyperpolymath/panic-attack: the interop contract, and one shared identity

[source,text]
----
TASK: answer two questions about the pons/panic-attack exchange, and settle
where the cross-producer identity is defined.

pons-asinorum is panic-attack's design companion (ADR-0004). The division of
labour is recorded in pons's docs/PURPOSE-AND-PROOF.adoc: panic-attack does
breadth/security/resilience, pons does depth/waste/contradiction, and they
"exchange versioned evidence while retaining independent analyses and
identities". The exchange is designed and never exercised.

1. CAN A NON-IDRIS PRODUCER EMIT THE PROOF-LADDER ARTEFACT?

contract_count=0; the gate is silent rather than green). But it does carry a
provenance ledger in the same tier vocabulary the framework uses — every test
entry is Actually-Proven / Provisionally-Proven / Unproven, and Actually-Proven
is unreachable here because proof_artifacts is empty. Question: can a producer
that is permanently Provisionally-Proven participate in the ladder at all, and
if so, what does it emit — an empty ladder file with a classification, an
explicit abstention, or nothing? The wrong answer is "emit something that
aggregate counts as coverage".

2. WHAT IS THE CANONICAL SELF-SCAN?
The estate's custom-tools-check invokes `panic-attack assail .` and `pons scan .`

source, with the flags you would stand behind? A documented invocation that a
repository can wire into CI for real would close the gap; the current situation
is that the gate is honest but unused.

3. THE ONE THAT ACTUALLY MATTERS — WHERE DOES CROSS-PRODUCER IDENTITY LIVE?
metadatastician/standards renders both tools in one verdict grid, and its

line, normalised defect class or CWE) — for panic-attack it uses `category`, for

semantic_fingerprint, which is (path, line, EVIDENCE class), because pons's unit

not be reconciled by making either tool adopt the other's.

     defect-class key can join both tools' output and neither has to invent a
     second identity scheme.
   * If no, then pons's site key stays site-scoped and cross-producer
     corroboration stays defect-class-scoped. That is the outcome pons expects;
     it is asking now so that its documentation stops implying otherwise.
Please answer with a decision, not an option list — pons will record whichever
answer you give in docs/EVIDENCE-CONTRACT.adoc.

Do not: relax panic-attack's own severity vocabulary to match pons's evidence
classes. The two are different axes and the grid normalises both already.

Permissions: none. This is a documentation and, at most, one optional field in

Installs: none.
