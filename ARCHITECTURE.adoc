= Pons architecture

The Rust workspace has four packages: `pons-core` owns source discovery,
grammars, findings, configuration and reports; `pons-rules` owns source and
repository checks; `pons-protocols` validates TOML contracts and explicit
ordered traces; `pons-cli` owns commands and bounded optional tool adapters.
The CLI entry point is `src/main.rs`, referenced by its package manifest.

Source discovery honours Git and Pons ignore files, skips symlinks and common
build/vendor directories, and bounds each supported text file to 2 MiB.
Invalid UTF-8 and tree-sitter parse errors make the scan incomplete. Original
UTF-8 bytes are retained for source locations; columns count Unicode code
points. AST rules inspect supported nodes. Repository rules compare the
collected sources. Reports retain diagnostics even when findings exist.

No scanned project code executes. `extract`, `spell`, `search` and `challenge`
are explicit commands that execute named local tools, with fixed argument
vectors, bounded input/output and a timeout. The default scan has no network
or external tool dependency. It does not recursively execute plug-ins named
by untrusted repository configuration.

Evidence strength is part of the finding schema. PROTOCOL means a checked
consequence of a stated model, not unconditional truth about a running
program. The implemented resource checker counts only supported literal
Python loops under an explicit consumption contract. The trace evaluator
checks supplied events and instance keys; it does not construct a CFG, infer
aliases, or prove the trace is complete. DATAFLOW has no implemented rules yet.

Language support is currently a compiled grammar registry plus Rust rule
implementations. User TOML patterns and contracts extend the checks without
executing arbitrary plug-in code. A versioned external plug-in protocol,
capability negotiation and language-specific CFG adapters remain future work.

Each built-in rule has a registered ID, an evidence class, a counter-condition
and mandatory positive/negative fixture cases. Failing the negative corpus
blocks CI; humans must repair, demote or remove the rule. The gate does not
silently change a rule's evidence classification.

JSON retains the Pons envelope and evidence. SARIF 2.1.0 supplies locations,
rule IDs, diagnostics, and evidence properties; speculative results have
note severity and lower rank. Separate scanners retain separate SARIF runs.
The container packages the core scanner as an unprivileged offline CLI.
Optional helper tools are not included in the minimal image.
